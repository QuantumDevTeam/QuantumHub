# Приёмы в коде

Здесь собрано то, что может быть незнакомо, с объяснением зачем оно здесь. Для тех приёмов, что заменили
что-то из прототипа, показано до и после.

## Что было хорошо в прототипе

Прежде чем разбирать отличия, стоит сказать, что идеи были верными, и они выжили:

- Разделение на `Contracts` и реализацию протокола.
- Единый конверт `HubMessage` с адресами отправителя и получателя, сейчас это `Envelope`.
- Интерфейс канала, за которым прячется транспорт.
- Сама ставка на файлы, отображённые в память, и protobuf.

Медленным был не замысел, а несколько конкретных вещей в реализации. Разберём их.

## Почему старый канал тормозил

### Поток из пула на каждое сообщение

```csharp
// Было
public Task WaitForDataAsync(CancellationToken token = default)
{
    return Task.Run(() => _dataReadyEvent!.WaitOne(), token);
}
```

`Task.Run` забирает поток из пула, а `WaitOne` блокирует его в ядре Windows. На каждое сообщение: запланировать
задачу, разбудить поток, переключить контекст, вернуться. Это десятки микросекунд, и ещё `token` здесь
ничего не отменяет: он проверяется только до старта задачи.

Теперь чтение идёт на одном выделенном потоке, и ядро он трогает, только когда данных долго нет.

### Массив на каждый приём

```csharp
// Было
Span<byte> buffer = new byte[input.Capacity];  // 64 КБ каждый раз
```

Массив выделялся на полный размер буфера, даже если сообщение занимало 100 байт. Он ещё и обнуляется при
выделении, а потом всё это собирает GC. Отсюда 133 КБ мусора на вызов.

Теперь буфер один на всё соединение и берётся из `ArrayPool`, смотри [Span и ArrayPool](#span-и-arraypool).

### MemoryMappedViewAccessor

`Accessor.WriteArray` и `ReadArray` ходят через маршалинг поэлементно. Теперь мы получаем указатель через
`SafeMemoryMappedViewHandle.AcquirePointer` и копируем как обычную память, смотри [unsafe](#unsafe-и-указатели).

### Один слот вместо очереди

Самая неприятная проблема, потому что она не про скорость:

```csharp
// Было
_accessor!.Write(0, data.Length);
_accessor.WriteArray(4, data.ToArray(), 0, data.Length);
```

Вторая запись перезаписывает первую, даже если её ещё не прочитали. А событие auto-reset склеивает два
сигнала в один. Тест с `Thread.Sleep(100)` этого не показывал, потому что сообщения шли медленно.

Кольцевой буфер решает это: у писателя своя позиция, у читателя своя, и пока между ними есть место, ничего
не теряется. Если места нет, писатель ждёт.

## Span и ArrayPool

`Span<byte>` — это окно на участок памяти: массив, стек или вообще указатель в общую память. Он не копирует
данные и не выделяет память. Поэтому один и тот же код `source.CopyTo(destination)` работает и с массивами, и
с кольцом в разделяемой памяти.

`ArrayPool<byte>.Shared.Rent(size)` выдаёт массив из пула, а `Return` возвращает его обратно. Вместо мусора на
каждое сообщение — несколько массивов на всё время работы. Смотри `FrameCodec.SendEnvelopeAsync`.

`Span` нельзя хранить в поле и нельзя держать через `await`, потому что он может указывать на стек. Если нужно
пережить `await`, берут `Memory<byte>`. Поэтому `IFrameChannel.SendAsync` принимает `ReadOnlyMemory<byte>`.

## ValueTask

`Task` — это объект в куче. Если операция почти всегда завершается сразу, выделять его жалко. `ValueTask` — это
структура, которая в быстром случае не выделяет ничего. `ShmFrameChannel.SendAsync` использует это: обычно
в кольце есть место и метод возвращает `default`.

Правило: `ValueTask` можно ждать только один раз и нельзя хранить.

## TaskCompletionSource: обещание, которое выполнит кто-то другой

`Task` обычно завершается сам. `TaskCompletionSource` создаёт задачу, которую ты завершишь вручную. Это мост
между «отправил запрос» и «когда-то потом на другом потоке пришёл ответ». Смотри шаг 1 в
[статье про сообщение](WALKTHROUGH.md).

`RunContinuationsAsynchronously` важен: без него код после `await` выполнился бы прямо на потоке чтения, и
если он надолго задержится, всё соединение встанет.

## Многопоточность без блокировок

### ConcurrentDictionary

Обычный `Dictionary` ломается при одновременной записи. `ConcurrentDictionary` делает это безопасно. Он
используется там, где читают и пишут постоянно: `_pending`, `_endpoints`, `_handlers`.

### ImmutableArray и копирование при записи

`Router._subscriptions` читается на каждое событие, а меняется редко. Поэтому список неизменяемый: рассылка
читает его вообще без блокировок, а подписка создаёт новый массив и подменяет ссылку через
`ImmutableInterlocked.Update`.

### Interlocked

Атомарные операции процессора. `Interlocked.Increment(ref _nextId)` гарантирует уникальный id без блокировки.
`Interlocked.Exchange` в `SignalClosed` и `Dispose` даёт приём «сделать ровно один раз».

### Channel

`Channel<T>` — потокобезопасная очередь с асинхронным чтением. `EventPump` кладёт в неё события и разбирает их
одной задачей, поэтому порядок сохраняется, а медленный обработчик не держит поток чтения.

## unsafe и указатели

Обычно C# не даёт работать с адресами. В разделяемой памяти нет объектов .NET, только байты по адресу, поэтому
`ShmRing` работает через `long*` и `byte*`. Это единственное такое место в проекте.

Цена: ошибка здесь — это не исключение, а `AccessViolationException`, который убивает процесс. Именно такой
баг нашёлся в тестах: если канал закрыть в момент между рукопожатием и стартом, читатель работал бы по
освобождённой памяти. Поэтому `ShmFrameChannel.Dispose` такой подробный, и лучше он намеренно оставит память до
конца процесса, чем рискнёт падением.

## Барьеры памяти

Самая трудная тема в проекте. Процессор и компилятор могут менять порядок операций с памятью, если в рамках
одного потока это незаметно. А между двумя ядрами заметно.

Представь читателя и писателя:

| Читатель | Писатель |
|---|---|
| Проверил: данных нет | |
| | Записал данные |
| | Проверил: читатель не спит, будить не надо |
| Лёг спать | |

Читатель спит вечно, хотя данные есть. Решение — делать проверку **после** объявления о намерении:

| Читатель | Писатель |
|---|---|
| Поднял флаг «сплю» | Опубликовал позицию |
| **Барьер** | **Барьер** |
| Проверил данные ещё раз | Проверил флаг |

Теперь хотя бы один обязательно увидит действие другого. `Interlocked.MemoryBarrier()` запрещает переставлять
операции через себя. `Volatile.Write` и `Volatile.Read` дают более слабую гарантию, но её хватает, чтобы данные
были видны раньше новой позиции.

## False sharing

Процессор кеширует память строками по 64 байта. Если `head` и `tail` лежат в одной строке, то ядра, пишущие
разные переменные, всё равно отбирают эту строку друг у друга на каждом сообщении. Поэтому в `ShmRing` счётчики
разнесены с шагом 64 байта.

## Почему размер кольца — степень двойки

`position % size` — это деление, а оно медленное. Если размер степень двойки, то `position & (size - 1)` даёт тот
же результат за один такт.

## AssemblyLoadContext

Обычно сборка загружается в процесс навсегда. `AssemblyLoadContext` — это отдельная область со своим набором
сборок. `PluginLoadContext` даёт две вещи:

- **Изоляцию версий.** Два плагина могут тянуть разные версии одной библиотеки.
- **Выгрузку.** С `isCollectible: true` область можно выгрузить и освободить файлы.

Подводный камень: типы равны, только если загружены одним контекстом. `IHubPlugin` из копии плагина и
`IHubPlugin` из копии хаба для .NET разные типы. Поэтому `Contracts` всегда берётся из хаба, а в проекте плагина
стоит `Private=false`.

Выгрузка завершится, только когда на код плагина не останется ни одной ссылки. Поэтому `LoadedPlugin.StopAsync`
так старательно всё отпускает, а `HubPayload.ResetJsonCache` чистит кеши `System.Text.Json`.

## Современный C#

Синтаксис, который встречается повсюду:

```csharp
// Primary constructor: параметры доступны во всём классе
public sealed class Router(Hub hub) { }

// Record: класс-значение, сравнение и ToString пишутся сами
public sealed record HubRequest(string Source, string Method, HubPayload Payload);

// required и init: обязательно задать при создании, потом нельзя менять
public required string ClientId { get; init; }

// Collection expression: [] вместо new List<...>()
public IReadOnlyList<Dependency> Dependencies { get; init; } = [];

// Диапазоны: первые first байт
source[..first]

// Сопоставление с образцом
case EnvelopeKind.Request when envelope is { Target: "hub", Method: "hub.ping" }:

// await using: вызовет DisposeAsync в конце блока
await using var client = await HubClient.ConnectAsync(options);

// Регулярка, собранная на этапе компиляции
[GeneratedRegex(@"^[A-Za-z0-9][A-Za-z0-9._-]*$")]
private static partial Regex ValidId();
```

## Решения на уровне дизайна

- **Запрет на блокировку в потоке чтения.** Всё долгое уходит в пул: иначе один медленный плагин
  останавливал бы целое соединение.
- **Ошибки как значения.** `Router.RequestAsync` никогда не бросает исключений и всегда возвращает ответ.
  Удобно, потому что ответ всё равно надо куда-то отправить.
- **Чистая логика отдельно.** `DependencyResolver` и `VersionRange` не трогают диск и процессы, поэтому их тесты
  мгновенные и простые.
- **Один объект на все роли.** `LoadedPlugin` реализует сразу шесть интерфейсов: всё, что держит плагин, держит один
  объект, и выгрузка становится проще.
