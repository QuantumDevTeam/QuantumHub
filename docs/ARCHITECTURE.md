# Архитектура

## Три части

**Хаб** (`QuantumHub.Service`) — источник истины. Держит конфиги, запускает плагины, маршрутизирует
сообщения. Что делает конкретный плагин, он не знает и знать не хочет.

**Плагины** — микросервисы этого сервера. Бывают двух видов, и код почти не отличается:
оба получают один и тот же `IHubBus`.

| | DLL-плагин | Внешний плагин |
|---|---|---|
| Где живёт | в процессе хаба | в своём процессе (Rider, Discord, отдельная программа) |
| Кто запускает | хаб | кто угодно, хаб лишь принимает подключение |
| Язык | .NET | любой |
| Цена вызова | вызов метода | ~6 мкс через shared memory |
| Упал | может уронить хаб (native crash, stack overflow) | хаб заметит и продолжит работу |

Частый случай — оба сразу. Счётчик строк: DLL в хабе хранит данные, а маленькие клиентские
части в Rider и VS Code только присылают события и объявляют первую зависимостью.

**GUI** — админка. Состояния у него нет, он подключается как обычный клиент. Закрыл окно, и
ничего не изменилось: плагины работают дальше.

## Решения, которые стоит знать

### Хаб — это фоновый процесс в сессии пользователя, а не Windows Service

Настоящий Windows Service живёт в session 0, где нет рабочего стола. Оттуда нельзя узнать
активное окно и нормально работать со звуковыми устройствами пользователя, то есть отвалились
бы именно те плагины, ради которых всё затевалось. Поэтому хаб стартует при входе пользователя
(ключ `Run` в HKCU, без прав администратора). Заодно каждый пользователь получает свой хаб, и
в именах pipe есть его SID.

То, ради чего обычно заводят службу, сделано по-другому. За падениями следит сторож: тот же exe с `--watch`
запускает хаб дочерним процессом и поднимает его снова, с растущей паузой и пределом в шесть падений за пять минут.
О выходе из Windows хаб узнаёт через скрытое окно и успевает остановить плагины. Служба от имени SYSTEM, которая
запускает хаб в сессии пользователя, здесь была бы ещё и опасна: программа стоит в папке пользователя, и любой
его процесс мог бы подменить exe и получить права SYSTEM.

### Рукопожатие по pipe, данные по shared memory

Клиент подключается к named pipe и шлёт `hub.hello`. Если он умеет shared memory, хаб создаёт
секцию с двумя кольцами, отдаёт её имя, и дальше все сообщения идут через память. Pipe при этом
не закрывается и становится «линией жизни»: когда процесс умирает любым способом, ядро Windows
рвёт pipe, и хаб узнаёт об этом сразу. Сама по себе shared memory этого сообщить не может.

Pipe выбран как базовый транспорт сознательно. Он тоже не трогает сетевой стек, а открыть его
может кто угодно: Node.js и JVM работают с ним как с файлом, то есть плагин для VS Code или
Rider обходится без нативных модулей.

Выбирает клиент, порядок предпочтения он передаёт сам:

| Транспорт | Когда | p50 на вызов |
|---|---|---|
| `shm` | C#, C++, всё, что умеет мапить память | ~6 мкс |
| `pipe` | Node, JVM, Python, скрипты | ~75 мкс |
| `tcp` | Среды без файлов и pipe. Выключен, включается флагом `--tcp <порт>`, требует токен из `endpoint.json` | — |

Новый транспорт — это один класс с `IFrameChannel`. OSC или WebSocket можно добавить так же,
или вообще отдельным плагином-мостом.

### Почему старый канал был медленным и как устроен новый

Замер на этой машине, запрос-ответ:

| | p50 | p99 | Аллокации на вызов | Условия |
|---|---|---|---|---|
| Старый | 49.5 мкс | 273 мкс | 133 КБ | один процесс, голый канал |
| Новый | 6.4 мкс | 15 мкс | 1.4 КБ | разные процессы, полный RPC с роутингом |

Что было не так:

- `Task.Run(() => WaitOne())` на каждое сообщение: прыжок через пул потоков и системный вызов на
  каждый приём. Токен отмены туда не доходил, отменить ожидание было нельзя.
- `new byte[Capacity]` на каждый приём, 64 КБ с обнулением. Отсюда и 133 КБ.
- `ViewAccessor.WriteArray/ReadArray`: медленный маршалинг вместо копирования памяти, плюс лишние
  копии через `ToArray` и временный массив.
- Один слот на сообщение. Вторая быстрая отправка затирала первую, если её ещё не прочитали, то
  есть сообщения терялись молча. Плюс сообщение не могло быть больше буфера.

Как сейчас (`ShmRing`):

- Кольцо на одного писателя и одного читателя, позиции — монотонные 64-битные счётчики. Быстрый
  путь обходится без системных вызовов: `memcpy` и атомарная публикация.
- Читатель сначала ~50 мкс крутится на позиции, потом засыпает на событии. Писатель трогает ядро
  только если читатель объявил, что спит. Гонка потерянного пробуждения закрыта полным барьером
  с обеих сторон. В простое хаб ест 0% CPU.
- Счётчики лежат в разных кеш-линиях, чтобы два ядра не перебрасывали одну и ту же линию.
- Кольцо — это поток байт, поэтому сообщение может быть больше кольца: 6 МБ через кольцо в 1 МБ
  проходят, писатель и читатель просто работают по очереди.
- Если кольцо заполнено, отправитель ждёт асинхронно и поток не занимает. Зависший клиент не
  блокирует хаб.

### Один конверт, а содержимое решает плагин

Всё по проводу — это `Envelope`: адрес, метод, `content_type` и байты `payload`. Хаб маршрутизирует
по адресу и в payload не заглядывает никогда. Внутри может быть protobuf, JSON или твой собственный
формат, и хабу нельзя помешать плагину изобрести новый.

Адресовать можно плагин по id, а можно возможность: `cap:system.specs`. Вызывающему всё равно, кто
её предоставляет, DLL или внешний процесс.

### Плагин делится на две DLL: сервис и UI

Хаб и GUI — разные процессы, поэтому один раз загрузить DLL на двоих нельзя в принципе. Но и
незачем: сервисная часть не должна тянуть WinUI в хаб. Так что манифест называет их отдельно
(`service` и `ui`). Загрузчики рассчитаны и на одну сборку в обоих полях, но этот вариант пока не
проверялся: примеры используют две DLL.

### UI плагина: декларативный, нативный или оба сразу

Настройки описываются в манифесте, и страницу для них строит хаб. Кода не нужно совсем.

**Декларативный UI** — дерево `UiNode`, которое плагин отдаёт по `ui.get`, а GUI рисует настоящими
контролами WinUI. Работает с любого языка и из любого процесса: страница для Rider-плагина может
прийти прямо из Rider.

**Нативный UI** — отдельная DLL с `INativePluginPage`, загружается в GUI и рисует что угодно. Пример:
лента в User Activity. Это даёт полную свободу, но только на .NET.

На страницах плагина эти варианты складываются во вкладки.

### Зависимости

Плагин зависит от другого плагина (`id`) или от возможности (`capability`), с диапазоном версий.
Главных переключателей два:

| | `when: "init"` | `when: "lazy"` |
|---|---|---|
| **обязательная** | без неё плагин ждёт, клиенту откажут в подключении с подробным ответом | проверится при первом запросе |
| **`optional: true`** | поднимется, если есть; нет, и ладно | ничего не грузится, пока не спросят; при отсутствии у клиента есть фолбэк |

Плагин с `"activation": "onDemand"` не занимает память, пока не нужен. Циклы определяются и
показываются в GUI с полным путём. Отключение плагина останавливает зависящих от него (они ждут в
состоянии `Blocked`), а включение поднимает их обратно.

Перезапуск устроен иначе: зависимые вообще не останавливаются. Подписки живут в роутере и переживают смену экземпляра,
а вызовы, пришедшие в этот момент, ждут конца перезапуска. Пропадает только то, что держал старый экземпляр: например,
список процессов, за которыми просили следить. Для этого плагин реализует `IDependencyAware` и после перезапуска повторяет
свои просьбы. Если зависимость не поднялась, зависимые переходят в `Blocked`, как при отключении.

Плагин может указать в манифесте поле `hub` с подходящими версиями хаба. Несовместимый плагин виден в списке с причиной,
но не запускается, а обновление на такую версию не трогает установленную.

### Окна плагинов живут в отдельных приложениях

Уведомления должны работать и при закрытом GUI, а хаб — фоновый процесс без окон. Поэтому всё, что плагин показывает на экране,
живёт в его внешней части: маленьком приложении, которое плагин запускает через `CompanionProcess`. Оно подключается к хабу
обычным клиентом, как внешний плагин, и закрывается, если хаб пропал. Сделаны такие части на WPF: прозрачные окна без фокуса в
WinUI 3 пока получаются плохо.

### Настройки описываются в манифесте

Хаб сам строит страницу настроек из манифеста: группы, списки, ползунки с значением, выбор. Поэтому улучшение этой страницы
получают сразу все плагины.

### Выгрузка плагинов

Каждый плагин грузится в свой collectible `AssemblyLoadContext`, поэтому удаление и обновление
работают без перезапуска хаба, и файлы реально освобождаются. Здесь есть один подводный камень:
`System.Text.Json` держит статические кеши по типам, и они не дают сборке выгрузиться. Хаб
сбрасывает их при выгрузке (`HubPayload.ResetJsonCache`), для этого используется внутренний
метод hot reload через рефлексию. Если в будущей версии .NET его не станет, ничего не сломается:
файлы будут удаляться при следующем старте, для этого есть отметка `.pending-delete`.

Плагин Music из памяти не выгружается: WinRT удерживает сборку до перезапуска хаба. Удалить и обновить его файлы это не мешает.

Нативный UI выгрузить нельзя, WinRT-объекты держат типы. Обновлённая UI-DLL подхватится после
перезапуска GUI.

## Где что лежит

```
<любая папка>/                       программа, может быть read-only
  QuantumHub.Service.exe
  gui/QuantumHub.Gui.exe
  dotnet/                            свой .NET: на компьютере ничего ставить не надо
  plugins/<id>/                      встроенные плагины и те, что поставил пользователь

%APPDATA%/QuantumHub/                всё пользовательское
  config/<id>.jsonc                  конфиг каждого плагина, хаба — в hub.jsonc
  data/<id>/  cache/<id>/            личные папки плагинов
  plugins/<id>/                      установленные, если в программу писать нельзя
  logs/
  endpoint.json                      куда подключаться
```

### Свой .NET рядом с программой

Плагины и внешние части выполняются на одном рантайме с хабом, поэтому полностью автономная сборка каждого exe заняла бы
гигабайт и всё равно не помогла бы внешним частям из файлов `.qhp`. Вместо этого в программе лежит одна папка `dotnet`.
Exe хаба и GUI ищут .NET в ней, а `CompanionProcess` передаёт путь внешним частям через `DOTNET_ROOT`. На компьютере
разработчика, где такой папки может не быть, всё работает на системном .NET.

Установщик собран иначе: одним файлом вместе с рантаймом, потому что запускается раньше, чем папка `dotnet` появится.

## Безопасность

Pipe открыт только текущему пользователю (`CurrentUserOnly`), первый экземпляр создаётся с
`FirstPipeInstance`, так что подменить хаб, заняв имя заранее, не выйдет. Секции памяти лежат в
`Local\` со случайными именами. Поле `source` заполняет хаб, клиент не может представиться чужим id.

Граница доверия при этом — пользователь. Любая программа, запущенная от того же пользователя, может
подключиться и, например, установить плагин. Это осознанно: такая программа и без хаба может всё то
же самое. DLL-плагин выполняется как обычный код без песочницы, так что ставить стоит только
плагины, которым доверяешь.

Ссылки `quantumhub://` приходят из недоверенных мест, поэтому им доступны только действия из манифеста, и первый запуск подтверждает пользователь.
Правила и то, как сообщить об уязвимости, описаны в [SECURITY.md](../SECURITY.md).

## Что сознательно не сделано

- **MSI и MSIX.** Есть свой установщик для одного пользователя, он не требует прав администратора.
- **Служба Windows.** Причина описана выше.
- **Автоматическая установка обновлений.** Окно сообщает о новой версии и ведёт на страницу релиза.
- **Подпись установщика и плагинов.** Для этого нужен сертификат.
- **Настоящие плагины для Rider и VS Code.** Протокол проверен клиентом на Python.
- **Клиент на C++.** Раскладка памяти описана в `PROTOCOL.md`, а сам клиент не написан.
- **IL-шаблоны из заметок.** Встроенные ресурсы и манифест в DLL покрывают те же задачи проще.
- **Зависимость DLL-плагина от внешнего клиента.** Разрешается, но при отключении клиента DLL-плагин
  не останавливается.
- **Комментарии в конфигах.** JSONC читается с комментариями, но хаб при записи их не сохраняет.
  В манифестах комментарии живут спокойно, их хаб не переписывает.
- **Два клиента с одинаковым `client_id`.** Адрес по id получает последний подключившийся, поэтому
  у частей плагина в разных IDE должны быть разные id.
